# The Persona Factory V2.1 — актуальная спецификация

Этот документ сохраняет V1 и первоначальную V2 ниже как исторический контекст.
Нормативной архитектурой проекта является V2.1.

V2.1 развивает главное решение V2: Persona Factory — внутренний Core Identity
Engine. Поиск трендов, аналитика охватов и внешние content-агенты не входят в
текущий MVP.

Ключевые уточнения V2.1:

1. Пять смысловых слоёв V2 сохраняются, но физически разделяются:
   `persona_rules`, `life_experiences`, `voice_examples` и `knowledge_chunks`.
   Regret является типом подтверждённого опыта, Style — подтверждёнными правилами
   плюс реальными примерами речи.
2. Книги не создают identity, beliefs или голос Мустафы. Они остаются knowledge
   либо явно выбираемой техникой `style_modes`.
3. Переписки используются только как `voice_examples`; факты и биография из них
   автоматически не извлекаются.
4. Любой новый факт или постоянное правило сначала становится
   `memory_candidate`/`pending` и активируется только через Telegram `/review`.
5. Генерируется один основной черновик. Альтернатива создаётся по запросу.
6. Длина выбирается явно: short, normal или expanded. Короткая мысль не должна
   автоматически превращаться в лонгрид.
7. Финальный preview обязателен; publish token обеспечивает идемпотентность.
8. Религиозные цитаты и нормы разрешены только из knowledge-записей со статусом
   `verified` и с отображаемым источником.
9. Production размещён на Railway. Схема Supabase использует vector(768).
10. Recency применяется к опыту и примерам голоса, но не обесценивает
    подтверждённые Identity-константы.

Полная operational-инструкция находится в `docs/PRODUCTION_ROLLOUT.md`.

# V1 — историческая концепция и дополнительные идеи

Системная архитектурная спецификация: "The Persona Factory"
ИИ-Операционная Система для Роста Личного Бренда и Контент-Генерации
## 1. Переосмысление концепции и цели проекта
The Persona Factory — это не просто имитатор общения («цифровой двойник»). Это персональная операционная система контент-мейкера, которая выступает в роли умного усилителя (Co-Pilot) автора.
### Главный сдвиг парадигмы (Почему это работает):
Большинство ИИ-персон терпят крах, потому что копируют только стиль речи (верхний слой). Настоящая уникальность автора рождается из его внутренней структуры. Наша система разделяет данные на три независимых вектора:
Убеждения (Beliefs Layer): Исламские ценности, отношение к финансам, этика в программировании. Это фильтр «что такое хорошо и что такое плохо».
Опыт (Experience Layer): Личные истории, факапы, победы (подготовка к ЕНТ, отказ от MBZUAI, занятия теннисом). Именно этот слой превращает безликий ИИ-текст в человеческий контент, который цепляет аудиторию.
Знания (Knowledge Layer): Сухие факты из загруженных книг и документации.
## 2. Технологический стек (100% Free Stack)

## 4. Правила обработки и хранения данных (Data Engine)
### Стратегия умного чанкирования (Chunking Strategy)
Слепое деление текста по 1000 символов ломает структуру религиозных и финансовых документов. Скрипт ingest.py разделяет логику обработки:
Категория "Программирование": Стандартное скользящее окно (1000 символов, перекрытие 200).
Категория "Ислам" и "Финансы": Семантическое чанкирование. Разрыв происходит строго на границах абзацев, аятов, хадисов или законченных смысловых тезисов (\n\n), чтобы избежать потери контекста при генерации.
### Структура баз данных в Supabase (Схема таблиц)
knowledge_chunks: id | content | embedding | category
personal_experience: id | story_tags | text_content | created_at (Логи жизненных историй: ЕНТ, теннис, Польша).
core_beliefs: id | topic | principle_rules | updated_at (Убеждения: отношение к долгам, халяль-инвестициям, чистой архитектуре).
content_intelligence: id | post_text | views | comments_count | reactions_score (Для анализа эффективности контента).
### Математическое ранжирование и управление временем (Recency Reranking)
Вместо переусложненных систем динамической памяти используется классический алгоритм реранжирования на основе косинусного сходства и экспоненциального затухания для слоя стиля:

### Модуль разрешения конфликтов (Conflict Detection)
Если ИИ находит два противоречивых правила в базе убеждений (например, старое «отвечать агрессией» и новое «отвечать спокойно»), оркестратор автоматически выбирает запись с максимальным updated_at (наиболее свежую), маркируя старую запись флагом is_deprecated=True в фоновом режиме.
## 5. Безопасность и Отказоустойчивость (Guardrails)
### Безопасность уровня доступа (Access Control)
В коде admin_bot.py на верхнем уровне хэндлеров жестко прописывается проверка ID создателя:
Python
MY_USER_ID = 123456789  # Ваш реальный Telegram ID

@dp.message()
async def handle_admin_commands(message: types.Message):
    if message.from_user.id != MY_USER_ID:
        return  # Бот полностью игнорирует любых посторонних пользователей
Все токены (Telegram, Gemini, Groq) хранятся в зашифрованных переменных среды (Environment Variables) на платформе хостинга.
### Цепочка автозамены моделей (Fallback Chain)
Если основной шлюз выдает ошибку лимита запросов (Rate Limit / Error 429), LiteLLM отрабатывает следующий каскад:
Первичный запрос: gemini-1.5-flash (Огромный контекст, бесплатный тариф).
Отказ 1: Перенаправление на groq/llama-3.1-70b (Высокая скорость, бесплатно).
Отказ 2: Асинхронное ожидание asyncio.sleep(5) + повторная попытка (максимум 3 раза).
## 6. Алгоритм работы контент-машины (A/B Тестирование)
Бот никогда не публикует контент автоматически. Он работает в режиме генерации вариантов.
Команда ввода: Вы пишете боту в приватный чат мысль: /idea Заметил, что регулярные занятия теннисом помогают мне структурировать код. Как связать это с дисциплиной в Исламе?
Сбор контекста: Оркестратор запрашивает:
Из personal_experience — историю про теннис.
Из core_beliefs — принципы дисциплины и исламские ценности.
Из knowledge_chunks — термины о структурировании кода.
Генерация вариантов (А/Б Тест): ИИ выдает сразу два черновика:
Вариант А (Прямой/Экспертный): Фокус на технологиях и коде через призму дисциплины.
Вариант Б (Рефлексивный/Исторический): Повествование через личную историю (Storytelling) и ценности.
Управление кнопками: Под сообщением выводятся инлайн-кнопки: [Опубликовать А], [Опубликовать Б], [Рерайт]. Выбор отправляет пост в канал через Telegram API.

# V2.0 — архитектурная основа V2.1 (историческая ревизия 2026)

### Ядро Цифровой Личности (Core Identity Engine) и Система Принятия Решений

---

## ## 1. Концептуальный парадигмальный сдвиг: Зачем и для чего?

Большинство систем имитации личности (AI Twins) терпят крах, превращаясь в безликих роботов, генерирующих цифровой шум. Ошибка кроется в попытке заставить одну LLM одновременно искать тренды, анализировать просмотры и «быть человеком».

Проект **The Persona Factory (V2.0)** жестко разделяет функционал на две суверенные системы:

1. **Внешний контентный контур (Будущее расширение):** Агенты-скауты, которые собирают тренды, парсят Threads/X/Telegram, анализируют кликабельность и формируют технические скелеты постов.
2. **Внутренний контур личности (Текущая система):** Хранилище смыслов, убеждений и личной истории Мустафы. Это «морально-этический и биографический фильтр».

### ### Как это работает в связке:

Когда внешний агент приносит горячий тренд (например, появление новой генеративной модели), он не имеет права писать пост сам. Он передает тему Внутреннему контуру. Ядро личности прогоняет тренд через фильтр ваших убеждений (Ислам, этика, системный подход) и извлекает из памяти релевантный жизненный выбор (например, ваш опыт ожидания решения от MBZUAI или подготовку к ЕНТ).

На выходе получается контент, обладающий **человеческой уникальностью**, который физически не способен сгенерировать ни один сторонний ИИ.

## ## 2. Модель данных: 5-уровневая Матрица Личности

Вместо плоской структуры RAG, Память Личности делится на пять строго изолированных иерархических слоев.

```
+-----------------------------------------------------------------------+
| 1. IDENTITY LAYER (Константы личности: глобальные цели, миссия)        |
+-----------------------------------------------------------------------+
                                   |
                                   v
+-----------------------------------------------------------------------+
| 2. BELIEFS LAYER (Фильтры ценностей: Ислам, этика бизнеса, ИТ-подход) |
+-----------------------------------------------------------------------+
                                   |
                                   v
+-----------------------------------------------------------------------+
| 3. EXPERIENCE & DECISIONS (Лог выборов: Контекст -> Решение -> Итог) |
+-----------------------------------------------------------------------+
                                   |
                                   v
+-----------------------------------------------------------------------+
| 4. REGRET & REFLECTION MEMORY (Архив ошибок, факапов и извлеченных уроков)|
+-----------------------------------------------------------------------+
                                   |
                                   v
+-----------------------------------------------------------------------+
| 5. STYLE & SYNTAX LAYER (Паттерны речи, маркеры тона, стоп-слова)     |
+-----------------------------------------------------------------------+

```

### ### Детальное описание слоев для базы данных:

1. **Identity Layer (Ядро Идентичности):** Долгосрочные жизненные константы. То, кем вы являетесь и куда идете в масштабе десятилетий.
* *Примеры:* Построение системного ИТ-бизнеса; помощь мусульманам в интеграции в индустрию ИИ; вера в жесткую внутреннюю дисциплину.


2. **Beliefs Layer (Слой Убеждений):** Моральные и профессиональные догмы. Система координат «правильно/неправильно».
* *Примеры:* Принципы халяльных финансов и инвестиций; отказ от неэтичных способов монетизации кода; важность регулярного духовного очищения как базиса для продуктивности.


3. **Experience & Decisions Layer (Дневник Решений):** Самый критически важный слой. Человека определяют его выборы в переломные моменты. ИИ должен знать хронологию и логику ваших ключевых решений.
* *Структура:* Контекст ситуации $\rightarrow$ Рассматриваемые опции $\rightarrow$ Финальный выбор $\rightarrow$ Последствия.
* *Примеры:* Отказ от учебы в Польше в пользу Казахстана; решение запустить блог в 2026 году.


4. **Regret & Reflection Memory (Память Ошибок):** База ваших уязвимостей, провалов и рефлексии. Идеальный ИИ отталкивает аудиторию; ИИ, понимающий цену ошибок, вызывает доверие.
* *Примеры:* Ошибки тайм-менеджмента, приводившие к выгоранию; упущенные возможности в кодинге; уроки, извлеченные из периодов спада мотивации.


5. **Style & Syntax Layer (Слой Стиля):** Лингвистический слепок. Формат предложений (короткие, емкие), использование терминов без академического занудства, специфический юмор, стоп-слова (слова, которые вы никогда не используете).

## ## 3. Технологический стек системы (100% Free Stack)

Архитектура разворачивается полностью в рамках бесплатных лимитов современных облачных платформ, исключая риск внезапной блокировки или требования оплаты.

| Компонент | Выбранная технология | Назначение | Ограничения Free Tier / Способ обхода |
| --- | --- | --- | --- |
| **Runtime Environment** | `Python 3.11+` | Исполнение всей логики, скриптов индексации и работы с векторами. | Нет ограничений. Локальный запуск + Docker-контейнер. |
| **AI Orchestrator** | `LangChain` + `LiteLLM` | Абстракция над LLM-провайдерами, сборка контекста из 5 слоев. | Нет ограничений. LiteLLM стандартизирует синтаксис под формат OpenAI. |

| **Production Hosting** | `Railway` | Контейнерный хостинг ядра и админ-бота. | FastAPI `/health`, restart policy и persistent volume для временных сессий. |
| **Primary Context LLM** | `Google Gemini 1.5 Flash` | Анализ глубоких логов, книг, извлечение паттернов личности. | **Лимит:** 15 запросов в минуту. Окно контекста в 1 000 000+ токенов полностью перекрывает потребности RAG. |
| **Fast Inference LLM** | `Groq API` (`Llama 3.1 70B`) | Мгновенная финальная сборка ответов и генерация черновиков. | **Лимит:** Динамические рейты. Используется как резервный слой (Fallback) и быстрый процессор. |

## ## 4. Схема Базы Данных (Supabase / DDL)

Для развертывания структуры в Supabase используется следующий SQL-скрипт. Он создает таблицы, учитывающие иерархию слоев, временные метки и векторы схожести.

```sql
-- Инициализация векторного расширения
CREATE EXTENSION IF NOT EXISTS vector;

-- 1. Таблица Знаний (Книги, статьи, документация)
CREATE TABLE knowledge_chunks (
    id BIGSERIAL PRIMARY KEY,
    content TEXT NOT NULL,
    embedding VECTOR(768), -- Фактическая размерность проекта
    category VARCHAR(50) NOT NULL, -- 'islam', 'finance', 'it'
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 2. Таблица Констант Идентичности и Убеждений
CREATE TABLE core_identity_beliefs (
    id BIGSERIAL PRIMARY KEY,
    layer_type VARCHAR(20) NOT NULL, -- 'identity' или 'beliefs'
    topic VARCHAR(100) NOT NULL,
    rules_and_values TEXT NOT NULL,
    is_deprecated BOOLEAN DEFAULT FALSE,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 3. Таблица Жизненного Опыта и Лога Решений
CREATE TABLE life_experience_decisions (
    id BIGSERIAL PRIMARY KEY,
    event_title VARCHAR(150) NOT NULL,
    context TEXT NOT NULL,
    choice_made TEXT NOT NULL,
    consequences_lessons TEXT NOT NULL,
    is_regret BOOLEAN DEFAULT FALSE, -- Флаг для слоя Regret Memory
    event_timestamp TIMESTAMP WITH TIME ZONE,
    embedding VECTOR(768)
);

-- 4. Таблица Лингвистического Стиля
CREATE TABLE style_patterns (
    id BIGSERIAL PRIMARY KEY,
    pattern_type VARCHAR(50) NOT NULL, -- 'stop_words', 'tone_markers', 'syntax'
    data_payload JSONB NOT NULL,
    confidence_score FLOAT NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

```

## ## 5. Математическое ядро и алгоритмы оркестрации

### ### Стратегия семантического чанкирования (Semantic Chunking)

Скрипт `ingest_knowledge.py` не имеет права резать текст книг по фиксированному лимиту символов.

* **Для ИТ-документации:** Применяется классическое скользящее окно (1000 символов, перекрытие 200) для сохранения целостности функций и кода.
* **Для Исламских и Финансовых текстов:** Разрыв чанков происходит строго по регулярному выражению `\n\n` или границам смысловых абзацев/глав. Смысловая целостность аята, хадиса или финансового правила имеет абсолютный приоритет над размером чанка.

### ### Алгоритм временного затухания памяти и реранжирования (Recency Reranking)

При извлечении данных из слоев опыта и стиля система обязана отдавать приоритет вашему актуальному состоянию (человек в 2026 году думает иначе, чем в 2022). Финальный вес извлеченного контекста ($Score$) рассчитывается оркестратором по формуле:

$$Score = S_{cos} \cdot e^{-\lambda \cdot t}$$

Где:

* $S_{cos}$ — косинусное сходство между вектором входящего запроса и вектором записи в БД.
* $t$ — количество дней, прошедших с момента создания записи (`created_at`) до текущей даты.
* $\lambda$ (лямбда) — коэффициент затухания, установленный на уровне $0.002$ (обеспечивает мягкое, но прогрессивное снижение веса старых воспоминаний при сохранении их семантической значимости).

### ### Модуль разрешения концептуальных конфликтов (Conflict Resolution)

Если входящий запрос активирует два эмбеддинга из таблицы `core_identity_beliefs` с противоположным смыслом, оркестратор применяет жесткий каскадный фильтр:

1. **Проверка активности:** Записи с `is_deprecated = True` полностью исключаются из контекста.
2. **Временной приоритет:** Выбирается запись с наибольшим значением `updated_at`.
3. **Логирование:** Конфликт записывается в системный лог для последующего ручного апдейта автором через админ-интерфейс.

## ## 6. Архитектура безопасности и отказоустойчивости (Guardrails)

### ### Авторизация на уровне системных событий (MY_USER_ID Gate)

Админ-бот защищен сквозной верификацией. Ни одно событие (текст, команда, инлайн-кнопка) не будет обработано ядром, если `user_id` отправителя не совпадает с глобальной константой создателя. Система полностью невидима для внешнего мира.

### ### Протокол каскадного падения (Fallback Chain)

Для обеспечения бесперебойной работы в условиях жестких лимитов бесплатных API, LiteLLM настраивается на автоматический каскадный роутинг запросов:

```
[Входящий запрос от Оркестратора]
               |
               v
     { Попытка №1: Gemini 1.5 Flash } ---> (Успех) ---> [Возврат текста]
               |
        (Ошибка 429 / Лимит)
               |
               v
     { Попытка №2: Groq / Llama 3.1 70B } -> (Успех) ---> [Возврат текста]
               |
        (Ошибка 429 / Сбой сети)
               |
               v
  [Асинхронная пауза asyncio.sleep(5)] ---> [Повтор цикла, макс 3 раза]
               |
      (Если всё отказало)
               |
               v
 [Системное уведомление автору о временном падении шлюзов]

```
